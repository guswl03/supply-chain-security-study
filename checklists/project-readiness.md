# 프로젝트 투입 준비 체크리스트

모든 항목을 외울 필요는 없습니다. 각 질문을 자신의 말로 설명하고, 모르는 내용을 어디에서 확인할지 알면 준비된 상태입니다.

## 개발·Git·패키지

- [ ] Git 브랜치, 커밋, PR의 차이를 설명할 수 있다.
- [ ] 브랜치 보호와 코드 리뷰가 공급망 공격을 줄이는 이유를 설명할 수 있다.
- [ ] 직접·전이 의존성을 구분할 수 있다.
- [ ] `package.json`과 `package-lock.json`의 차이를 설명할 수 있다.
- [ ] `npm install`과 `npm ci`의 사용 목적을 구분할 수 있다.
- [ ] npm lifecycle script의 위험을 설명할 수 있다.
- [ ] API 키가 Git에 올라갔을 때 삭제만으로 충분하지 않은 이유를 설명할 수 있다.

## CI/CD·빌드

- [ ] CI와 CD의 차이를 설명할 수 있다.
- [ ] 워크플로 변경이 코드 변경만큼 중요한 이유를 설명할 수 있다.
- [ ] 빌드 러너의 권한과 비밀정보 위험을 식별할 수 있다.
- [ ] SBOM, 해시, 전자서명, 출처 증명의 역할을 구분할 수 있다.
- [ ] SLSA가 해결하려는 문제를 한 문장으로 설명할 수 있다.

## 클라우드·컨테이너

- [ ] 클라우드 공동책임 모델을 설명할 수 있다.
- [ ] 이미지, 컨테이너, 레지스트리의 관계를 설명할 수 있다.
- [ ] 이미지 태그와 다이제스트의 차이를 설명할 수 있다.
- [ ] 이미지 스캔과 이미지 서명이 다른 이유를 설명할 수 있다.
- [ ] IAM 최소 권한과 단기 자격증명의 장점을 설명할 수 있다.
- [ ] IaC 변경을 리뷰해야 하는 이유를 설명할 수 있다.

## 네트워크·배포

- [ ] DNS, HTTP, HTTPS, TLS의 기본 역할을 설명할 수 있다.
- [ ] TLS와 파일 서명이 서로 다른 대상을 보호한다는 것을 설명할 수 있다.
- [ ] 패키지·이미지·업데이트의 이동 경로와 신뢰 경계를 그릴 수 있다.
- [ ] 협력사 원격접속이 공급망 위험이 되는 이유를 설명할 수 있다.
- [ ] 정상 업데이트 경로가 공격에 악용되는 시나리오를 작성할 수 있다.

## SBOM·취약점

- [ ] SBOM이 보장하는 것과 보장하지 않는 것을 설명할 수 있다.
- [ ] Source, Build, Deployed, Runtime SBOM의 차이를 이해한다.
- [ ] CVE, CVSS, EPSS, KEV, VEX를 구분할 수 있다.
- [ ] 구성요소 포함 여부와 실제 사용·도달 가능성의 차이를 설명할 수 있다.
- [ ] 취약점의 우선순위를 점수 하나로 정하면 안 되는 이유를 설명할 수 있다.
- [ ] 패치, 완화조치, 격리, 예외 승인의 차이를 설명할 수 있다.

## AI 공급망

- [ ] 데이터, 코드, 프레임워크, 모델, 모델 허브, API를 공급망으로 연결할 수 있다.
- [ ] 모델 카드와 SBOM의 역할 차이를 설명할 수 있다.
- [ ] 신뢰할 수 없는 모델 파일을 바로 실행하면 안 되는 이유를 설명할 수 있다.
- [ ] 모델의 정확도와 공급망 안전성이 다른 평가라는 것을 설명할 수 있다.
- [ ] 외부 모델과 데이터의 출처·버전·라이선스·해시를 확인할 수 있다.

## 관리·대응

- [ ] 개발사, 공급사, 운영사의 책임을 구분할 수 있다.
- [ ] 제3자와 제4자 위험의 차이를 설명할 수 있다.
- [ ] 오픈소스 라이선스 의무를 확인해야 하는 이유를 설명할 수 있다.
- [ ] 취약점 발견부터 영향 분석, 통보, 조치, 복구까지의 흐름을 작성할 수 있다.
- [ ] 프로젝트의 구현 범위와 제외 범위를 정할 수 있다.
- [ ] 탐지율, 오탐률, 분석시간 등 평가 지표를 정의할 수 있다.

## 판정

- 80% 이상: 프로젝트에 바로 투입 가능한 기초 수준
- 60~79%: 프로젝트 진행과 병행해 부족한 영역 보완
- 60% 미만: 사전 준비와 1~3주차 핵심 내용을 우선 복습
