# 1주차: 개발·오픈소스 공급망

난이도: ★★☆☆☆

선행지식: 없음

## 이번 주 목표

코드가 외부 패키지를 포함해 빌드 산출물이 되는 흐름과, 그 과정에서 신뢰가 어떻게 형성되는지 이해합니다.

```text
개발자 → Git 저장소 → 외부 패키지 → 빌드·테스트 → 배포 파일
```

### GitHub 저장소 보안

- 브랜치 보호와 강제 푸시 제한
- 필수 PR 리뷰와 작성자·승인자 분리

- Personal Access Token과 SSH 키 관리

- GitHub Actions 워크플로 변경 검토
- 외부 Action을 태그가 아닌 커밋 SHA로 고정하는 이유

### API, npm, axios의 관계

- **API**: 프로그램끼리 기능이나 데이터를 요청하고 응답하는 약속
- **npm**: Node.js 프로젝트에서 외부 패키지를 설치하고 관리하는 도구 및 공개 패키지 생태계
- **axios**: JavaScript에서 HTTP API를 호출할 때 사용할 수 있는 외부 npm 패키지

```text
npm 저장소
  ↓ axios와 하위 의존성 설치
내 프로그램
  ↓ HTTP API 요청
외부 API 서버
  ↓ 응답 데이터
내 프로그램
```

이 흐름에는 두 종류의 공급망이 존재합니다.

1. **패키지 공급망**: npm에서 axios와 하위 패키지를 가져오는 과정
2. **서비스 공급망**: axios를 이용해 외부 API와 데이터를 주고받는 과정

### npm 프로젝트의 주요 파일

| 항목 | 역할 | 공급망 관점의 확인사항 |
|---|---|---|
| `package.json` | 사용할 패키지와 버전 범위 정의 | 과도하게 넓은 버전 범위, 불필요한 패키지 |
| `package-lock.json` | 실제 설치 버전, 다운로드 위치, 무결성 정보 고정 | 잠금 파일 변조, 코드 리뷰 없는 변경 |
| `node_modules` | 내려받은 패키지의 실제 파일 | 직접·전이 의존성, 설치 후 생성된 파일 |
| npm registry | 패키지를 배포·다운로드하는 저장소 | 패키지 계정 탈취, 악성 패키지, 저장소 신뢰 |

### 버전과 설치 재현성

- Semantic Versioning: `MAJOR.MINOR.PATCH`
- 정확한 버전, `^`, `~` 범위의 차이
- `dependencies`와 `devDependencies`
- `npm install`과 `npm ci`
- 설치 전·후 실행되는 npm lifecycle script
- 오래됐거나 유지관리되지 않는 패키지

프로젝트와 CI에서는 잠금 파일을 함께 관리하고 `npm ci`로 고정된 의존성을 설치하는 흐름을 이해합니다. 잠금 파일은 설치 결과를 재현하는 데 도움을 주지만, 이미 악성인 패키지나 알려지지 않은 취약점까지 제거하지는 않습니다.

## 4. 미니 실습

Node.js와 axios를 이용한 작은 예제 프로젝트를 사용합니다.

```bash
npm init -y
npm install axios
npm list --all
npm audit
npm ci
```

1. `package.json`에서 axios의 버전 범위를 확인합니다.
2. `package-lock.json`에서 실제 버전, 다운로드 위치, 무결성 정보를 확인합니다.
3. `npm list --all`에서 axios 외에 설치된 하위 패키지를 찾습니다.
4. axios를 직접 의존성, axios가 사용하는 패키지를 전이 의존성으로 구분합니다.
5. `npm audit` 결과가 무엇을 근거로 판단했는지 확인합니다.
6. 안전한 공개 테스트 API에 GET 요청을 보내 요청·응답 흐름을 확인합니다.
7. 구성요소명, 버전, 출처, 사용 목적을 표로 정리합니다.
8. 가능하면 SBOM을 생성해 npm의 의존성 목록과 비교합니다.
9. `npm install`과 `npm ci`가 잠금 파일을 처리하는 방식을 비교합니다.
10. `package.json`의 `scripts` 항목과 설치 스크립트가 실행할 수 있는 동작을 확인합니다.

도구 실행 자체보다 결과가 실제 프로젝트와 일치하는지 확인하는 것이 중요합니다.

### axios API 호출 예시

```javascript
const axios = require("axios");

async function main() {
  const response = await axios.get(
    "https://jsonplaceholder.typicode.com/todos/1"
  );
  console.log(response.data);
}

main();
```

실습에서는 임의의 API 키를 코드에 넣지 않습니다. 인증이 필요한 경우 환경변수와 실습용 키를 사용하고, `.env` 파일은 Git에 커밋하지 않습니다.

### 실습 후 공급망 분석

| 확인 대상 | 질문 |
|---|---|
| axios | 누가 만들고 어디에서 배포하는가? |
| 하위 의존성 | 내가 직접 선택하지 않은 패키지는 무엇인가? |
| 잠금 파일 | 실제 설치 버전과 무결성이 고정됐는가? |
| npm 저장소 | 패키지의 이름과 제작자를 어떻게 확인하는가? |
| 외부 API | 제공자가 침해되거나 응답이 변조되면 어떤 영향이 있는가? |
| API 키 | 어디에 저장되고 어떤 권한을 가지고 있는가? |

## 5. 토론 질문

- 외부 패키지를 사용하지 않는 개발은 현실적인가?
- 많은 사람이 사용하는 패키지는 더 안전한가?
- SBOM에 기록됐다는 사실이 안전성을 의미하는가?
- 개발자는 어디까지 하위 의존성을 책임져야 하는가?
- `npm audit`에 경고가 없으면 안전하다고 말할 수 있는가?
- 외부 API를 라이브러리와 같은 공급망 의존성으로 봐야 하는가?
- HTTPS와 npm의 무결성 검사는 각각 무엇을 보호하는가?
