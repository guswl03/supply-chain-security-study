# 1주차: 개발·오픈소스 공급망

난이도: ★★☆☆☆

선행지식: 없음

## 이번 주 목표

코드가 외부 패키지를 포함해 빌드 산출물이 되는 흐름과, 그 과정에서 신뢰가 어떻게 형성되는지 이해합니다.

```text
개발자 → Git 저장소 → 외부 패키지 → 빌드·테스트 → 배포 파일
```

## 1. 먼저 익힐 기초

- 프로그램, 소스코드, 실행 파일
- 라이브러리, 패키지, 프레임워크
- Git, GitHub, 리포지토리, 커밋
- 패키지 관리자
- 직접 의존성과 전이 의존성
- 빌드, 테스트, 배포
- CI/CD 기초

## 2. 공급망 보안 개념

- SW 공급망과 SDLC
- 공개 SW와 제3자 구성요소
- 취약한 패키지와 악성 패키지의 차이
- 타이포스쿼팅과 의존성 혼동
- 개발자 계정·토큰 탈취
- 악성 커밋과 빌드 시스템 변조
- SBOM의 역할과 한계

## 3. 사례 분석

### 필수: Log4Shell

- Log4j가 제품에 어떻게 포함됐는가?
- 조직은 왜 포함 여부를 바로 알지 못했는가?
- 취약점과 공급망 문제는 어떻게 연결되는가?

### 선택: Codecov 또는 XZ Utils

`진입점 → 악용된 신뢰 → 변조·취약 대상 → 전파 → 영향 → 가능한 통제`로 정리합니다.

## 4. 미니 실습

작은 Python 또는 Node.js 예제 프로젝트를 사용합니다.

1. 패키지 하나를 직접 설치합니다.
2. 전체 의존성 트리를 확인합니다.
3. 직접·전이 의존성을 구분합니다.
4. 구성요소명, 버전, 출처를 표로 정리합니다.
5. 가능하면 SBOM을 한 번 생성해 내용을 읽습니다.

도구 실행 자체보다 결과가 실제 프로젝트와 일치하는지 확인하는 것이 중요합니다.

## 5. 토론 질문

- 외부 패키지를 사용하지 않는 개발은 현실적인가?
- 많은 사람이 사용하는 패키지는 더 안전한가?
- SBOM에 기록됐다는 사실이 안전성을 의미하는가?
- 개발자는 어디까지 하위 의존성을 책임져야 하는가?

## 완료 기준

- [ ] 코드부터 배포 파일까지의 흐름을 그렸다.
- [ ] 직접·전이 의존성을 설명할 수 있다.
- [ ] 취약한 패키지와 악성 패키지를 구분할 수 있다.
- [ ] 사례 한 건을 공급망 관점으로 분석했다.
- [ ] 예제 프로젝트의 구성요소 목록을 작성했다.
